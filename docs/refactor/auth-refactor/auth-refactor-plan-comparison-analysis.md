# 认证重构计划文档对比分析

> 日期：2026-03-29
> 目的：对比 3 份针对同一认证重构任务生成的方案文档，评估优劣、分析影响计划质量的因素，并给出后续协同使用建议。

---

## 一、对比对象

本次对比文档：

1. `auth-refactor-opencode-glm5_1.md`
2. `auth-refactor-trae-glm5_1.md`
3. `auth-refactor-opencode-mimo.md`

---

## 二、综合结论

综合排序：

1. `auth-refactor-opencode-glm5_1.md`
2. `auth-refactor-trae-glm5_1.md`
3. `auth-refactor-opencode-mimo.md`

结论说明：

- `opencode-glm5_1` 最适合作为主方案基线。它抓住了真正影响运行时安全和行为的核心问题，尤其是 AI 模块认证缺失、`NotLoginException` 未正确处理、`UserContext` fallback 掩盖问题等。
- `trae-glm5_1` 更擅长补充清理项和编译闭环，例如死代码、示例配置、残留常量引用等，但它把范围扩展到了 `AuthServiceImpl` 的 refresh token 机制调整，超出了当前“统一认证方案”的最小必要范围。
- `opencode-mimo` 偏保守，更多是在做温和清理和废弃标记，没有覆盖当前最关键的 AI 模块认证缺口，也没有形成足够完整的执行闭环。

因此，更推荐的使用方式不是“三选一”，而是：

- 用 `OpenCode` 产出主方案
- 用 `Trae` 做局部补洞和审校
- 最后回到主方案进行收敛

---

## 三、各文档优缺点

### 1. `auth-refactor-opencode-glm5_1.md`

优点：

- 能基于代码现状识别高严重度问题，而不是只做表面清理
- 关注运行时行为与安全风险，不止关注代码整洁
- 输出结构完整，包含步骤、依赖关系、影响范围和验证清单
- 更适合作为实际开发计划的主线文档

不足：

- 少量收尾不够完整，例如未同步清理 `ChatController` 中对 `HEADER_USER_ID` 的死代码引用
- 未覆盖 `WebMvcProperties.java` 和 example 配置清理这类残留项

总体评价：

- 主方向最正确
- 适合作为基线方案
- 需要补少量“清理闭环”内容

### 2. `auth-refactor-trae-glm5_1.md`

优点：

- 文件级清单更细，补充了死代码、example 配置、残留配置类等问题
- 更关注“删完之后能否顺利编译”的闭环
- 在局部补全方面表现较好

不足：

- 对 AI 模块认证问题判断偏保守，将高风险问题弱化为后续可选优化
- 把方案范围扩展到 refresh token 机制优化，增加了任务风险和不确定性
- 计划看起来更“完整”，但部分内容已经偏离当前任务主线

总体评价：

- 适合做补充审校
- 不适合直接作为当前任务的唯一主方案

### 3. `auth-refactor-opencode-mimo.md`

优点：

- 改动保守，风险感知较低
- 对“最小改动”有一定意识

不足：

- 没有覆盖 AI 模块认证缺失这一关键问题
- 主要是“标记废弃”，没有真正完成统一和清理
- 未覆盖异常处理、依赖清理、自动配置清理等关键环节
- 更像建议草稿，不像可执行开发计划

总体评价：

- 可作为轻量参考
- 不适合作为本次重构的执行文档

## 四、决定开发计划生成质量的因素

从这次对比来看，影响方案完备性的主要因素如下。

### 1. 代码上下文获取质量

- 是否真正查看了关键 Java 文件、配置文件、`pom.xml`、自动配置、异常处理器
- 是否验证了“看起来像死代码”的内容到底是否真的不生效
- 是否覆盖跨模块调用链，而不是只看单个模块

这是影响质量最大的因素之一。上下文拿不全，方案一定会漏。

### 2. 问题边界是否定义准确

- 当前任务到底是“统一认证链路并清理残留”
- 还是“顺手重构 refresh token 机制”

边界不清时，文档容易出现两种问题：

- 方案过窄，只做表面清理
- 方案过宽，把无关优化混入主计划

### 3. 模型本身的推理风格

- 有些模型善于抓主问题，但容易漏收尾项
- 有些模型善于补充细节，但容易扩需求

这不是单纯的“聪明程度”差异，更像是推理取向差异。

### 4. 系统提示词与 Agent 规则

- 是否强调基于代码事实
- 是否强调最小改动
- 是否要求验证清单
- 是否要求区分已确认事实与推断

同一个模型，在不同规则下输出风格可能差异很大。

### 5. 工具链能力

- 是否方便全局搜索、读多文件、查看配置和依赖
- 是否容易交叉验证 controller、config、pom、yml、exception 等多个层次

工具越方便，越容易形成完整闭环。

### 6. 用户输入质量

如果任务描述只说“帮我分析怎么重构”，通常更容易发散。更优的输入方式应明确：

- 目标
- 范围
- 不做什么
- 输出格式
- 验收方式

### 7. 是否存在第二轮审校

单次直接生成完整计划，很容易漏文件、漏风险、漏验证项。

更稳的方式是：

- 第一轮产出主方案
- 第二轮做定向审校
- 第三轮收敛为最终执行计划

## 五、IDE 影响大吗

IDE 有影响，但通常不是决定性因素。

更准确地说，大家平时感知到的“IDE 差异”，往往是下面几个因素叠加后的结果：

- IDE 的默认系统提示词
- IDE 提供的上下文注入方式
- 工具链能力和调用便利度
- 可承载的上下文长度
- 与模型的集成方式

因此，不能简单根据这一次结果下结论说：

- `TRAE` 一定比 `OpenCode` 更优秀
- 或 `OpenCode` 一定比 `TRAE` 更优秀

本次样本更能说明的是：

- `OpenCode + glm5_1` 在“主问题识别和主线收敛”方面更适合作为完整方案基线
- `Trae + glm5_1` 在“补充清理项和细节审校”方面有优势

这属于工作流适配差异，不足以证明某个 IDE 在整体上绝对更强。

## 六、推荐工作流

推荐采用以下协同方式：

### 阶段 1：用 OpenCode 产出主方案

目标：

- 识别主问题
- 确定边界
- 列出最小可落地闭环方案
- 输出执行顺序和验证清单

这一阶段要避免方案过度发散。

### 阶段 2：用 Trae 做局部审校

目标：

- 检查是否遗漏受影响文件
- 检查是否存在编译风险
- 检查是否有残留死代码、示例配置、常量引用
- 只补洞，不重写主方案

### 阶段 3：回到 OpenCode 收敛最终计划

目标：

- 只吸收必要补充项
- 拒绝无关扩展项
- 形成最终执行文档

## 七、如果用 OpenCode 做完整方案，需要注意什么

为了让 `OpenCode` 更稳定地产出“完整且不过度扩展”的方案，建议遵循以下原则。

### 1. 明确写清任务边界

建议在提示词中显式说明：

- 本次只处理什么
- 本次不处理什么
- 不要顺手重构无关内容

例如：

- 只处理认证链路统一和旧 JWT 清理
- 不改对外接口语义
- 不重做 refresh token 机制
- 不做无关重构

### 2. 要求区分“已确认事实 / 推断 / 待确认”

这能显著降低“把猜测写成结论”的概率。

### 3. 要求覆盖完整检查面

建议明确要求它检查：

- Java 代码
- yml 配置
- `pom.xml`
- 自动配置
- 异常处理
- 常量引用
- 调用链影响

### 4. 强制输出完整受影响文件清单

最好要求按以下分类输出：

- 删除文件
- 新增文件
- 修改文件
- 需确认文件

这对防止漏项特别有效。

### 5. 让它先做事实核对，再做方案输出

比起一步生成完整方案，更推荐两轮式：

1. 第一轮只确认现状问题
2. 第二轮再生成开发计划

### 6. 明确要求“最小闭环方案优先”

建议在提示词中加入：

- 优先给最小可落地闭环方案
- 可选优化项必须单独列出
- 不要把未来演进项混入当前主计划

### 7. 用 Trae 审校时要定向，不要开放式重做

不要让 `Trae` “重新生成一个更好的完整方案”，而应明确要求它只检查：

- 漏文件
- 编译风险
- 配置遗漏
- 死代码遗漏
- 运行时风险

这样更容易发挥两者互补优势。

## 八、推荐提示词模板

### 1. OpenCode 主方案模板

```md
请先基于代码事实分析，不要先给泛化建议。

任务目标：
统一当前认证方案，清理旧 JWT 残留，并补齐缺失认证链路。

范围约束：
- 只处理当前认证体系相关代码、配置、依赖
- 不修改对外接口语义
- 不扩展到 refresh token 机制重做
- 不做无关重构

请输出：
1. 已确认事实
2. 问题清单（按严重度排序）
3. 最小可落地方案
4. 受影响文件清单（删除/新增/修改/需确认）
5. 执行顺序
6. 验证清单
7. 可选优化项（与主方案分开）

要求：
- 必须核对 Java 代码、yml、pom、自动配置、异常处理
- 明确区分“已确认事实 / 推断 / 待确认”
- 方案优先最小改动和闭环，不要顺手扩需求
```

### 2. Trae 审校模板

```md
请不要重写完整方案，只做补充审校。

请检查这份方案是否存在：
1. 漏掉的受影响文件
2. 编译风险
3. 配置清理遗漏
4. 死代码/常量/引用遗漏
5. 运行时风险点

输出格式：
- 必补项
- 可补项
- 不建议纳入本次范围的项
```

## 九、最终建议

如果目标是“生成更稳、更完整、但不过度扩展的开发计划”，推荐策略如下：

1. `OpenCode` 负责主方案
2. `Trae` 负责局部补洞和审校
3. 最终回到主方案进行收敛

这套方式比单独依赖任一工具都更稳，也更符合工程上“先抓主问题，再补闭环细节”的思路。

不建议基于这一次样本就下结论说 `TRAE` 比 `OpenCode` 更优秀。更合理的结论是：

- `OpenCode` 更适合收敛主线和形成执行方案
- `Trae` 更适合做局部微调和补充审校

两者协同使用，效果最好。
